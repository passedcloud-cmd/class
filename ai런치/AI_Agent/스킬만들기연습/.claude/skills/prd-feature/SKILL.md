# PRD 먼저 정리하기 (prd-feature)

## 왜 이 스킬이 필요한가

"로그인 기능 추가해줘" 같은 요청은 겉보기엔 간단해 보이지만, 실제로는 소셜 로그인 포함 여부, 비밀번호 찾기 흐름, 세션 유지 시간, 에러 처리 방식 등 수많은 결정이 숨어 있습니다. 이런 결정을 임의로 내리고 코드부터 작성하면 사용자의 실제 의도와 어긋난 결과물이 나오기 쉽고, 재작업 비용이 커집니다. 그래서 짧고 모호한 기능 요청을 받으면, 코드를 작성하기 전에 대화를 통해 요구사항을 구체화하고 PRD로 정리하는 단계를 먼저 거칩니다.

## 언제 사용하는가

**사용한다:**
- "OO 기능 추가해줘", "OO 페이지 만들어줘"처럼 한두 문장짜리 기능 요청
- 무엇을 만들지는 말했지만 범위·동작·예외 처리가 정해지지 않은 요청

**사용하지 않는다:**
- 사용자가 이미 상세 스펙, API 명세, 유저 스토리, 수용 기준을 제공한 경우 (이 경우 그 내용을 요약 확인만 하고 바로 진행)
- 버그 수정, 오타/문구 수정, 기존 코드 리팩터링, 설정값 변경처럼 "새로운 것을 정의"하는 게 아니라 "이미 정의된 것을 고치는" 요청
- 사용자가 명시적으로 "질문 없이 바로 코드로 만들어줘"라고 요청한 경우 (이때는 스킵하되, 임의로 내린 주요 가정을 코드와 함께 짧게 알려준다)

## 진행 절차

### 1단계 — 요청 파악
사용자의 요청에서 이미 알 수 있는 정보(기능명, 힌트가 되는 맥락, 기존 코드베이스의 관련 파일)를 먼저 파악한다. 이미 답이 나와 있는 질문은 다시 묻지 않는다.

### 2단계 — 질문하기 (한 번에 하나씩, 대화하듯)
질문은 한꺼번에 쏟아내지 않고, 하나씩 던지고 답을 들은 뒤 그 답을 바탕으로 다음 질문을 조정한다. 사용자가 이미 답한 내용은 다시 묻지 않는다. 아래 항목을 자연스러운 순서로 다루되, 이미 명확한 항목은 건너뛴다.

- **목표/배경**: 이 기능이 왜 필요한가? 어떤 문제나 불편을 해결하는가?
- **유저 스토리**: 누가(어떤 사용자가) 이 기능을 쓰는가? 무엇을 하기 위해 쓰는가?
- **범위 (In / Out of scope)**: 이번에 반드시 포함할 것과, 의도적으로 제외할 것은 무엇인가?
- **성공 기준**: 이 기능이 완성됐다고 판단하는 기준은 무엇인가? (예: 특정 동작이 되면 성공, 특정 지표가 개선되면 성공)
- **기술적 고려사항/제약**: 기존에 쓰는 기술 스택, 연동해야 할 기존 코드/API, 성능·보안·데이터 관련 제약이 있는가?

질문 방식:
- 자유 서술이 필요한 질문(목표/배경, 유저 스토리 등)은 짧은 텍스트 질문으로 직접 묻는다.
- 선택지가 명확히 나뉘는 질문(예: "저장 방식을 파일로 할지 DB로 할지")은 AskUserQuestion 같은 선택형 질문 도구를 활용해도 좋다.
- 사용자가 "잘 모르겠다", "네가 정해줘"라고 답하면, 코드베이스와 일반적인 관례를 참고해 합리적인 기본값을 제안하고 "이렇게 진행해도 될까요?"라고 확인만 받은 뒤 다음 질문으로 넘어간다. 답을 억지로 받아내려 하지 않는다.
- 질문 개수는 꼭 필요한 만큼만. 이미 요청 문장에 답이 있거나, 사소해서 구현하면서 자연스럽게 정해질 항목은 묻지 않는다.

### 3단계 — PRD 작성
질문과 답변이 끝나면 아래 템플릿에 맞춰 PRD를 작성한다.

```markdown
# PRD: {기능명}

## 배경 / 문제
{왜 이 기능이 필요한가, 어떤 문제를 해결하는가}

## 목표
{이 기능으로 달성하려는 것. 목표가 아닌 것도 명시하면 좋다}

## 유저 스토리
- {사용자 유형}로서, 나는 {행동}을 하고 싶다. 왜냐하면 {이유}.

## 범위
### In scope
- {이번에 포함할 것}

### Out of scope
- {이번엔 제외할 것 (나중에 할 수도 있음을 명시)}

## 성공 기준
- {완료 판단 기준. 가능하면 확인 가능한 형태로}

## 기술적 고려사항 / 제약
- {기존 스택, 연동 대상, 성능/보안/데이터 제약 등}

## 미해결 질문 (선택)
- {합의되지 않았거나 구현하며 정해야 할 것}
```

### 4단계 — 파일로 저장
PRD를 `docs/prd/{기능-슬러그}.md`에 저장한다 (예: `docs/prd/login-social-auth.md`). `docs/prd/` 디렉터리가 없으면 새로 만든다. 같은 이름의 파일이 이미 있으면 덮어쓰기 전에 사용자에게 확인받는다.

### 5단계 — 확인 후 구현
PRD 저장 후 사용자에게 내용을 검토해달라고 요청한다. 사용자가 PRD 내용에 동의하거나 수정을 마친 뒤에만 실제 코드 구현을 시작한다. PRD 없이, 또는 사용자 승인 없이 바로 구현으로 넘어가지 않는다.
