Tool-use(Function Calling)
주의
LLM이 함수를 직접 실행하는 것이 아님
LLM이 하는 일 : "get_order_status 라는 도구를 order_id='ORD001' 로 호출해줘" 라는 JSON을 생성
실제 실행 :  우리 파이썬 코드가 그 JSON을 읽고 함수를 호출
LLM은 여전히 텍스트(JSON)만 생성한다. 실행은 우리 쪽 코드가 한다.
-> 이 사실이 중요한 이유: 실행 직전에 우리가 개입할 수 있다는 뜻이다. 5장의 검증 로직과 HITL(사람 승인)이 가능한 근거가 바로 여기에 있다.

"description": "주문 상태를 조회한다. 주문번호를 입력하면 현재 상태를 반환."
description은 독스트링을 읽고 tool 데코리터가 작성함
중요! @tool에서 독스트링은 주석이 아니라 프롬프트


issue_coupon도 한도 초과 시 예외가 아니라 "발급 실패: 한도 초과"라는 문자열을 반환
-> 문자열을 반환해야 LLM이 문자열을 읽고 왜 실패했는지 이해하기 때문 

2-4. LLM만으로는 행동 못함
쿠폰을 발급했다고 하든 발급 못했다고 했든
실제발급된 쿠폰은 비어있음.
LLM은 텍스트만 생성했을 뿐 아무 일도 일어나지 않음

2-5. 

bind_tools()를 한 LLM은 "이 도구를 이렇게 호출해줘"라고 요청만 한다. 실행은 하지 않는다.
bind_tools()          ->  LLM이 tool_calls 를 반환 (요청서)
create_react_agent()  ->  요청서를 읽고 실제로 실행까지 (자동화)
👉 그래서 다음 두 셀을 반드시 순서대로 실행하며 차이를 봐야 한다.



LLM이 요청한 도구 호출:
  도구: get_order_status_tool, 인자: {'order_id': 'ORD001'}
-> LLM은 tools = [get_order_status_tool, issue_coupon_tool]이라는 2개의 도구 중에서 get_order_status_tool만 사용함
LLM이 요청서를 만들었으므로
실행을 따로 해야 함

agent = create_react_agent(model=llm, tools=tools, prompt=system_prompt)를 실행하자 진짜로 쿠폰이 발급됨 



[HumanMessage] 주문 ORD001의 상태를 확인하고, 배송 지연이면 5000원 쿠폰을 발급해줘.
[AIMessage] 도구 호출 -['get_order_status_tool']
[ToolMessage] 주문번호: ORD001, 상태: 배송 지연, 상품: 노트북
*AI가 '배송 지연'을 보고 다른 tool을 호출함 
[AIMessage] 도구 호출 -['issue_coupon_tool']
[ToolMessage] 쿠폰 발급 완료: 주문 ORD001에 5,000원 쿠폰 발급
[AIMessage] 주문 ORD001의 현재 상태: 배송 지연
-> AI는 도구를 2번 사용함. 만약 더 많은 도구가 필요했다면 더 사용했을 것. 우리는 요청을 1번 했는데 에이전트는 도구를 여러 번 씀. 에이전트의 실행 속도가 느리고 토큰 소모량이 큰 이유.



LLM은 기본적으로 각 요청을 독립적으로 처리한다
해결책은 단순하다: 이전 대화를 매번 함께 보내면 된다. <- 메모리 기능

3-3 MemorySaver 동작 원리
대화 1: "내 주문번호는 ORD001이야"
  → MemorySaver가 저장: {thread_id: "user123", messages: [...]}
대화 2: "그 주문 상태 알려줘"
  → MemorySaver가 thread_id="user123"의 이전 대화를 불러옴
  → Agent가 ORD001을 기억하고 상태 조회
고객마다 다른 thread_id를 부여.

메모리를 생성하니 이전 대화의 주문번호를 기억함
주문번호를 바꾸면 모름


4. ReAct
chain of tought에 손을 달아준 것
COT : 생각 -> 생각 -> 생각
React: 생각 -> 행동 -> [관찰] -> 생각 
React는 환각에 강한 편임. 도구가 실제로 반환한 값을 근거로 다음 단계를 정하기 때문

업무를 나눠서 시키는 것 - 비용이 증가하는 건 어쩔 수 없음

품질이 중요할 때 멀티 에이전트 사용
