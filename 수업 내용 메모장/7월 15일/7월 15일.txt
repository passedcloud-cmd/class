팀원들이 초대를 받아 권한을 받는 것


git push origin master
원격 저장소에 push할 거다. origin이라는 이름의 원격저장소에, master 브랜치를.

git push origin feature/login
더이상 master를 push하는 게 아는 것.

master는 merge를 통해서 불어나는 것.

pull request(PR): master에 내 브랜치를 받아달라는 요청. 코드 리뷰를 거친 뒤 합치거나 반려하거나 수정하거나 함.

요즘은 코파일럿이 코드 리뷰를 알아서 해줌

보류할 거 보류하고 수정할 거 수정해야 함.

각 사용자 로컬이 갖고 있는 master는 github로부터 병합된 master를 pull하여 업데이트 해야 함.

Fork는 자신의 계정으로 복사하는 것
파이썬 깃헙 원본에는 push할 수 없음. 
나는 cpython 팀원이 아니라서 레포지토리에 바로 PR할 수 없음.
cpython 그걸 내 project에 fork해서 뜸.
내 project는 내 거니까 PR을 생성할 수 있음.
그걸 다시 cpython으로 PR 보낼 수 있음.


내가 복제한 (origin)에 내가 만든 브런치를 올림
PR을 생성하면 원본으로 보내짐.
만약 원본에서 내가 보낸 걸 받았다면 
그걸 pull해서 받아옴
원본에 contributors에 내 이름이 올라오게 됨.




Unit Test
회귀 버그: 잘 되던 기능이 다른 기능을 넣으면서 깨짐.
그래서 검증을 해야 함

unit test(단위 테스트)

검증 대상과 그 아래에 검증 코드를 넣어야 함.
검증 코드는 1)준비 단계 2) 실행 단계 3) 검증 단계가 있음
 		-> AAA패턴이라고 함

기능 구현마다 "AAA패턴을 기반으로 한 단위 테스트를 진행해라" 명령어 넣기
태스트 코드를 짜줘.


예시) 바이브 코딩으로 계산기 구현

1단계: 계산기를 만든다
2단계: 테스트 코드를 붙인다.
3단계: 새 기능을 추가
4단계: 일부러 기능을 망가지게 해서 테스트 코드를 확인.

테스트 코드를 너무 맹신하지 말 것




어디에 테스트를 꼭 붙여야 하는지 확인해 함.
예시)
테스트를 꼭 붙여야 하는 곳
- 포인트 제도(계산)
- 게시글 삭제 조건 (데이터 삭제 조건이 올바르게 동작하는지)
- 로그인/권한 판별

테스트를 안 붙여도 되는 곳
- 버튼 색깔, 폰트 크기
- 화면이 움직이는 애니메이션

테스트 커버리지: 작성한 테스트 케이스가 소프트웨어의 전체 코드 또는 요구 사항 중 어느 정도의 비율을 실행하고 검증해야 하는지 측정하는 지표.
높다고 해서 무작정 좋은 거 아님. 주요 기능 위주로 테스트 해야 함.

1. 게시글 등록
2. 게시글 삭제
3. 챗봇에 메시지를 보내면 응답 형식에 맞게 오는가
